<objective>
Fix QA BUG 1 (QA-01): terminal-query replies generated by xterm.js are forwarded to the shell as keystrokes. On attach, tmux (and shells) send terminal queries; the browser's xterm.js answers them (`ESC[?1;2c` DA1, `ESC[>0;276;0c` DA2, `ESC]10;rgb:...` and `ESC]11;rgb:...` colour replies); `TerminalView` forwards every `onData` event as `agent:input`; the gateway writes it to the pty; the shell prints `1;2c0;276;0c` and the next command is corrupted (`0cecho qa-broadcast-ok`, "Command '0cecho' not found").

The real path (verified): `term.onData` in `src/components/agent/TerminalView.tsx` is the only place that forwards xterm data. `AgentControls` sends only literal user actions (`\x03`, `clear\r`), `BroadcastBar` uses `agent:broadcast`, `term.onBinary` is not wired anywhere, and the gateway (`SessionManager.sendInput` to `driver.write`) writes frames to the pty verbatim by design. xterm 5.5.0 emits every automatic reply through `coreService.triggerDataEvent(data)` (`InputHandler.ts`, `Terminal.ts`), the same event user keystrokes use; the public `onData` does not say which is which.

Fix layer and why (choice justified, per the request to prefer xterm's own API): register query handlers on `term.parser` (`registerCsiHandler`, `registerDcsHandler`, `registerOscHandler`). A custom handler that returns true stops xterm's built-in handler, so the reply is never generated and nothing needs to be recognised afterwards. Rejected alternatives, each verified against the installed xterm 5.5.0 source:
- `onBinary` instead of `onData`: replies use `triggerDataEvent`, not `triggerBinaryEvent`; `onBinary` only carries legacy-encoded mouse reports, so it cannot separate replies from keystrokes.
- A stateful filter on the `onData` stream: the reply bytes are not distinguishable from input. A Shift+F3 key press is exactly `ESC[1;2R` (verified in jsdom), which is also the CPR reply for cursor row 1, column 2; a bracketed paste of reply-looking text is legitimate. A byte filter either eats a real key or misses a reply.
- A filter in the gateway: it sees opaque frames with the same ambiguity, and the browser is where the reply is created.
- A terminal option that disables reports: none exists except `windowOptions`, which already defaults to every report off (and is also guarded here).
Chunk-boundary robustness comes for free: the xterm parser keeps its state across `write` calls, so a query split over two `agent:output` frames is still one query. The cost is a deliberate one: applications that ask xterm for device attributes, colours or the cursor position get no answer (they fall back to defaults after their own timeout, which is the documented behaviour of a terminal that does not support a query). The suppression table is data, so one family can be re-enabled by deleting its row if a later application needs it.

Scope: only xterm-generated answers to queries are suppressed (DA1, DA2, DA3, DSR/CPR and DEC private DSR, DECRQM, XTVERSION, window-state reports, DECRQSS, XTGETTCAP, and the OSC 4/10/11/12 colour queries). Focus reports (`ESC[I`, `ESC[O`) are not touched: xterm only emits them after the application enabled mode 1004, in which case they are requested input. Mouse reports likewise.

Purpose: restore a clean prompt and correct broadcast results (QA steps 1e and 3), and close a terminal-report injection class (attacker-controlled output making the terminal type text into the shell).
Output: `terminalReports.ts`, its wiring in `TerminalView.tsx`, new tests, and a Troubleshooting entry in `docs/RUNNING.md`.
