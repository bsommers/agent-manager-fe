<objective>
QA BUG 3, reclassified by the user (QA-03): closing an agent in the UI must NOT kill its tmux session; that behaviour (the gateway removes the agent and detaches its pty, the session keeps running) is correct and stays. What is missing is an explicit way to kill a tmux session. This plan delivers the protocol and gateway half; plan 09.1-04 (wave 5) delivers the "Kill tmux session..." UI action behind DestructiveSafetyModal, the docs and the QA driver steps.

Design choice (the request asked for the cleaner of `tmux:kill_session {sessionName}` and `agent:kill {id, killSession:true}`): `agent:kill` with an optional `killSession` flag, for these reasons grounded in the protocol package and the contract spec:
- The session name stays server-side. With `tmux:kill_session` the client supplies a name that the gateway must then validate and match against its registry; with the flag the client supplies only an agent id the gateway already knows, so "only a session the gateway knows about or discovered" holds by construction.
- One atomic roster operation: the gateway ends the session, closes the driver, drops the agent and announces one snapshot. A separate message would leave the agent pane in a dangling disconnected state that needs a second close.
- Backend-agnostic: the spec's agent model is generic (cvm, climah, ssh have no tmux). A tmux-named message type would be the only backend-specific message in the contract; a flag on kill lets other adapters answer `UNSUPPORTED` or map it to their own session notion.
- Additive: new optional fields are classified additive by the contract rules (no `CONTRACT_VERSION` change), whereas a new message type adds a table row and a new FE call path.
Reversibility: the fields are on the wire but only this repo consumes them today; undoing them is a contract edit across the package, the gateway and one FE call site.

Gateway-enforced confirmation (requirement added during planning): the gateway decides whether a kill goes ahead, not the browser. The message carries `confirm: true`; when `killSession` is true and `confirm` is not exactly true the gateway answers the requesting client with a typed `agent:error` (code `USAGE`) and runs nothing. `DestructiveSafetyModal` in the UI is only the UX that sets `confirm`; it is not the safety check. This is an explicit-intent gate against accidental or buggy callers (devtools, scripts, a future FE regression), not an authorization boundary: a client that wants to can set the flag, and authentication is Phase 8. It is deliberately small: one field on one message, no general operations catalog (that comes later).

Security design (execFile only, no shell, strict validation): the session name comes from `tmuxSessionNameOf(agent.targetHost)` (identical rule to the drivers: the part after the first colon, else the whole string), must match `^[A-Za-z0-9_][A-Za-z0-9_-]{0,63}$` (no colon or dot, which tmux rewrites in names and uses in target syntax; no leading hyphen; no whitespace or shell metacharacters), and is passed as `tmux kill-session -t =<name>` where the `=` prefix demands an exact match instead of tmux's default prefix and pattern matching. `execFile` gets an argument array, a timeout, and no `shell` option. Sessions with other names (for example containing a space) can still be killed by hand with `tmux kill-session -t <name>` (documented by 09.1-04).

Typed replies: `handleClientMessage(msg, reply?)` gains an optional reply callback; `server/src/index.ts` passes one that writes a single frame to the requesting socket if it is still open (one line added there). Refusals and failures of the kill-session path are answered with `agent:error` through it (`retryable: false`, `agentId` included only when it is a valid id of at most 128 characters, fixed message text, no `reqId` echo until Phase 6 adds correlation). The FE does not handle `agent:error` yet, so the UI still learns of an unconfirmed kill through its existing 10 s timeout notice; Phase 6 and 9 consume the typed errors.

Ordering versus plan 02-04 (same wave, which owns root `package.json`, `.github/workflows/ci.yml`, `packages/protocol/src/{surface,index}.ts`, `packages/protocol/contract.snapshot.json`, `packages/protocol/scripts/**`, `packages/protocol/tsconfig*.json` and `packages/protocol/README.md`): the files are disjoint, but 02-04 generates the surface snapshot from the validator tables as they are at its base commit, so the merged tree will contain validator fields that the snapshot does not describe.
