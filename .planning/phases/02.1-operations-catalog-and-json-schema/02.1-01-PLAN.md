<objective>
Generate one JSON Schema from the FieldSpec tables in `packages/protocol`, check it in, make `contract:check` fail on drift, pin every integer field, and prove the schema against the existing fixtures (INT-12, ROADMAP Phase 2.1 criterion 1).

Purpose: the validators are TypeScript only. Adapters in other languages (cvm, climah, bilterm in Phase 28) and the later MCP facade need a language-neutral description of the same contract that cannot drift from it.
Output: `jsonschema.ts` generator, `scripts/generate-schema.ts`, committed `contract.schema.json`, a schema-drift check in `scripts/contract-check.ts`, in-repo test evaluator, conformance tests, `SCHEMA.md`.

Design decisions (planner discretion, no CONTEXT.md exists for this phase):
- Draft 2020-12 (default dialect of MCP and supported by ajv, Python jsonschema, Go and Rust validators). `$defs` keys are flat and prefixed: `Agent`, `client.<type>`, `server.<type>`, `http.<kind>`, plus unions `ClientMessage` and `ServerMessage`.
- The schema describes what a conforming SENDER emits, so it is strict on enums, bounds and integer-ness, and it never forbids unknown fields (the contract says receivers ignore them). Receiver tolerance (an enum value dropped instead of rejected, unknown capabilities filtered) is recorded as an `x-dropUnknown` annotation, not modelled. The validators in `validate.ts` remain normative.
- Constraints JSON Schema cannot express are annotations (`x-maxBytes`, `x-trim`, `x-maxDepth`, `x-maxChars`, `x-rules`), never silently dropped.
- Regeneration is a script (`npx vite-node packages/protocol/scripts/generate-schema.ts`), not a new npm script: root `package.json` belongs to plan 05-04 in this wave. Folding it into `contract:update` is a one-line follow-up after 05-04 merges and is deliberately not part of this plan.
- Not exported from `src/index.ts`: that file belongs to the sibling plan 02.1-02 in this wave. The check script and tests import `../src/jsonschema.js` directly; Phase 21.1 adds the barrel export when the gateway needs `objectSpecToSchema` for MCP tool input schemas.

Interface agreed with sibling plan 02.1-02 (same wave, disjoint files, no dependency either way): this plan creates `packages/protocol/SCHEMA.md`, `packages/protocol/contract.schema.json` and `packages/protocol/scripts/generate-schema.ts`; plan 02.1-03 (wave 6, after both) documents them in `packages/protocol/README.md` and the contract spec by exactly these paths. The schema is generated from the tables only, and 02.1-02 keeps every table row byte-identical, so the two plans can merge in either order.

Package installs: none. Threat T-02.1-SC is accepted for that reason. If an adapter test suite or Phase 28 later wants ajv as a devDependency it must be added after plan 05-04 has merged (it owns the root `package.json`), with a Package Legitimacy Audit in that phase's RESEARCH.md.
</objective>
