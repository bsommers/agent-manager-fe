<objective>
Add one operations catalog to `packages/protocol` that drives the protocol surfaces: WS validators, HTTP routes and the MCP tool list derive from it (the palette identities are exported from it), tests fail when a surface and the catalog disagree in either direction, and `contract:check` classifies the catalog addition as additive (INT-12, ROADMAP Phase 2.1 criteria 2-4; the FE palette derivation, contract spec section 4.3 and the README are plan 02.1-03 in wave 6).

Purpose: Phase 6 builds the gateway service layer and its destructive policy from the `destructive` flag; Phase 21.1 builds an MCP facade from the tool list; every later surface (Phase 16 search route, Phase 22 palette command) adds an operation once and the tests tell it where it is missing.
Output: `specs.ts`, `operations.ts`, derived rows in `validate.ts`, an `operations` section in the surface and snapshot with change classification, catalog tests, the public exports through `index.ts`.

Split note: this plan was cut from three tasks to two. The former Task 3 (palette derivation in `src/keyboard/commands.ts`, spec cross-check test, contract spec section 4.3, README) is now plan 02.1-03 (wave 6, depends on this plan); it needs only this plan's exports. Nothing else about Tasks 1 and 2 changed.

Design decisions (planner discretion, no CONTEXT.md exists for this phase):
- Twelve operations, not the eight named in the criterion. The criterion lists the existing agent operations; the catalog must also cover every other client WS message and every HTTP route of contract spec section 7, otherwise the "surface lists an operation the catalog lacks" test would need an allowlist for agent:history, agent:approve, GET /api/agents and GET /api/agents/:id/logs. Only hello and ping (handshake and heartbeat) and the probes GET /health and GET /api/health are exempt, as two named exported lists.
- Close and kill are two operations sharing the WS message type agent:kill, selected by the boolean killSession (Phase 9.1). The message type owns one validator row (the `row` owner is agent.kill); agent.close takes a subset of its params as the same spec objects.
- `destructive` plus `confirmParam` is what Phase 6 enforces at the gateway: refuse with a typed agent:error unless the named param is exactly true. This plan only records it and gives Phase 6 `operationForClientMessage`. `DELETE /api/agents/:id` is bound to agent.close; agent.kill has no HTTP binding because contract section 7 defines no confirm form for it (Phase 6 adds it, additively).
- Bindings the contract does not define are `{ none: reason }`, never omitted, so a missing surface is a visible, reviewed statement.
- The catalog holds only the palette command id (a palette binding is `{id}`, with the three bound ids agent.new, broadcast.open and search.open matching the existing palette commands); titles, hints and every other UI string stay in the FE, and the palette derivation is plan 02.1-03. `PaletteOperationName` (the union of operation names whose palette binding is bound) is exported here so plan 02.1-03 can key its command record by it and make a palette binding without a command a compile error.

Ownership and ordering (wave 5): this plan owns `packages/protocol/src/{specs,operations,validate,index,surface}.ts`, the snapshot and the three test files above. It does not touch `packages/protocol/README.md`, the contract spec or `src/keyboard/commands.ts` (all three are owned by plan 02.1-03 in wave 6; plan 05-04 and later plans must keep their edits out of `src/keyboard/commands.ts`), root `package.json` or lockfiles (plan 05-04 owns them), `packages/protocol/{SCHEMA.md,contract.schema.json,scripts/**,src/jsonschema.ts}` (sibling plan 02.1-01), or anything under `server/`. No package is installed.

Interface agreed with sibling plan 02.1-01 (no dependency either way; merge in any order): it creates `packages/protocol/SCHEMA.md`, `packages/protocol/contract.schema.json` and `packages/protocol/scripts/generate-schema.ts` (regenerate with `npx vite-node packages/protocol/scripts/generate-schema.ts`); plan 02.1-03 links to them by those paths in README and the spec. This plan keeps every client, server and http table row byte-identical, so the generated schema does not change when both plans are merged.
