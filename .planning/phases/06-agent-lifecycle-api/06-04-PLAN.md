<objective>
INT-03 gateway half 2 and Phase 6 criterion 5 (gateway side): replace the "full snapshot after every mutation" announcement with the contract's `agent:added`, `agent:removed` and `agent:updated` events, so several surfaces (WS clients, the HTTP API of 06-06, later MCP) can create and remove agents and every connected UI learns about it incrementally while a new or reconnecting connection resyncs from one `agent:init_list`.

Locked decisions honoured (docs/CHECKPOINT.md): closing an agent never kills tmux (the `removed` event for a close says only that the agent left the roster); the gateway enforces destructive operations (this plan touches no policy); port 8088 untouched; no token in URLs. The FE half (applying these events, reconnect resync proof, docs) is plan 06-05 in this wave; it already works with the snapshots that the gateway sends until this plan merges, and applies events idempotently afterwards, so the two plans merge in either order.

Why events replace snapshots instead of accompanying them: a snapshot per mutation costs O(roster) per change for every client and invites the FE to treat a snapshot as an acknowledgement (the Phase 10 pending claim by field equality that 06-03 removed). The contract (section 4.2) already defines the three events for this phase, and `agent:init_list` remains "a full, idempotent snapshot" for connects. Compatibility: a pre-Phase-6 FE (which applies only snapshots) against this gateway keeps a stale roster until it reconnects; FE and gateway of this repository are released together (documented in 06-05).

Reversibility: `costly` (a wire-semantics change that the FE, the QA driver and later adapters depend on; undoing it means re-adding the snapshot publish in three places and reverting the FE). Not one-way: nothing is persisted, and the contract version does not change (events were already in the contract).

What stays: `SessionManager.addClient` still sends the snapshot first on connect; the gateway-wide broadcast fan-out; `agent:status_change`; the 06-01 spawn-failure rule (a failed create publishes nothing).

Coverage (source audit): GOAL and success criterion 5 (gateway: `agent:added/removed/updated` emitted, init_list resync without duplicates) are covered here; FE application is 06-05. REQ INT-03. Not planned: `agent:removed` reasons other than `killed` (`exited`, `gone`, `backend_down` need adapters and persistence: Phases 11 and 20), `epoch` or sequence numbers on events (Phase 11).
</objective>
