<objective>
INT-03 gateway half 1 and GW-04 (WS wrapper): put one validated, typed dispatch path in front of the service layer of 06-01 and give the client the contract's request correlation. After this plan a client that sends `reqId` on `agent:create`, `agent:kill` or `agent:update` receives exactly one `agent:ack` (or one `agent:error` carrying the same `reqId`), a repeated `reqId` is idempotent, the gateway validates every client frame with the package validators and answers malformed ones with `agent:error USAGE`, and the WS handler is a thin wrapper (parse, execute, map outcome to frames).

Locked decisions honoured (docs/CHECKPOINT.md): the order is service layer (06-01), then `reqId` with acks and adopting the 09.1 `agent:kill { agentId, killSession, confirm }` message (done here: the message is routed through dispatch unchanged, its confirm refusal and replies preserved), with the FE handling of `agent:error` in plan 06-03 (same wave, disjoint files) and the catalog-driven destructive policy in 06-07; closing never kills tmux (close and destroy stay distinct service calls); the gateway, not the FE modal, enforces destructive operations (the service gate from 06-01 is untouched); port 8088 is not touched (tests bind port 0); no token appears in a URL or frame.

Design decisions made here (recorded in the spec by Task 3):
- `reqId` stays optional on the wire. The roadmap says correlation is "required, not polish": that is a client rule (the FE always sends it, plan 06-03) enforced by tests there, not a schema change, because making a field required is a breaking contract change and the spec (section 4.2) promises requests without `reqId` behave as before. Consequence: a pre-Phase-6 client keeps working against this gateway; the FE of 06-03 requires a Phase-6 gateway (until Phase 8 adds `hello_ack` gating, documented in the spec).
- Broadcast acks, per-target results delivery and broadcast idempotency stay with Phase 12 (INT-05). `agent:broadcast` runs through dispatch and the service but is not acked.
- `agent:input` and `agent:resize` carry no `reqId` and never produce a reply, including for an unknown agent, so a dead agent cannot turn every keystroke into an error frame. Oversize input is the one exception: it is rejected at validation with `PAYLOAD_TOO_LARGE` (contract section 6.2) because dropping it silently loses user data; a frame over 65536 UTF-8 bytes was previously written to the pty and is now refused (FE chunking is Phase 12 and 14 work; plan 06-03 surfaces the error).
- Post-mutation roster snapshots are left alone here (still broadcast after create and close); 06-04 replaces them with `agent:added/removed`. The unknown-id snapshot quirk of 06-01 is removed (NOT_FOUND now).

Reversibility: `reversible` (additive fields and replies; git revert restores the old switch).

Coverage (source audit): GOAL and success criteria 2 (typed outcomes, reqId correlation, gateway side), 4 (validation and USAGE), 6 (idempotent reqId, WS side; the HTTP side is 06-06) and 1 (thin WS handler) are covered here; REQ INT-03 and GW-04. The FE half of criteria 2 and 3 is 06-03; added/removed/updated announcements and resync are 06-04 (gateway) and 06-05 (FE) (criterion 5); HTTP routes 06-06; destructive policy from the catalog 06-07 (criterion 7). Out of scope by design: broadcast acks (Phase 12), rate limiting (Phase 12), auth (Phase 8), `hello`/`hello_ack` (Phase 8).
</objective>

- `server/src/index.ts` per-socket handler: parses JSON inside one try block; a non-object, array or frame without a string `type` throws `Error('Client frame must be a JSON object with a string "type"')` and is logged once as `console.error('Invalid WebSocket message received:', err)`; invalid JSON is logged the same way; `ping` is answered with `pong` (ignored when `t` is not a finite number) before any other handling; everything else is passed to `sessionManager.handleClientMessage(parsed, reply)` where `reply` writes one frame to that socket if it is still open. `hardening.test.ts` pins: non-object frames log exactly once with that message; an unknown `type` produces no console output; invalid JSON is logged and the socket stays usable. - The package validator: `parseClientMessage(input)` returns `{ ok: true, msg }` (a copy with unknown fields stripped) or `{ ok: false, reason, field?, detail? }` with `reason` in `not_object | missing_type | unknown_type | invalid_field`; it never throws. `operationForClientMessage(msg)` returns the operation name for a parsed message (`agent.close` versus `agent.kill` for `agent:kill`) and null for `hello` and `ping`. `LIMITS.MAX_INPUT_BYTES` is 65536; `reqId` is a string of 1 to 128 characters wherever it appears; `agent:error` and `agent:ack` shapes are in `SERVER_TABLE` (`AckOp` is create, kill, update or broadcast).

- The package validators reject a non-boolean `confirm` or `killSession`.
