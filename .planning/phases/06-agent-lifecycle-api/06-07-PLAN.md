<objective>
GW-05 (Phase 6 criterion 7): make the destructive-operation policy a property of the operations catalog enforced at the gateway, not a hard-coded check inside one handler. Phase 9.1 already made the gateway refuse `agent:kill { killSession: true }` without `confirm: true`; that check lives in the service and in the WS path. This plan (a) lifts the rule into a policy stage derived from the Phase 2.1 catalog's `destructive` flag and `confirmParam`, applied in the one dispatch path that WS and HTTP (and later MCP) share, (b) gives the destructive operation its HTTP form so the policy is proven on a second surface, and (c) proves the rule by a test that walks the catalog.

Locked decisions honoured (docs/CHECKPOINT.md): closing an agent must not kill tmux (`agent.close` stays non-destructive on `DELETE /api/agents/:id`, `agent.kill` is the only destructive operation and the only one that touches tmux); the gateway enforces destructive operations, not just the FE modal (this plan is that decision made structural); the Phase 6 order puts this plan after the service layer, `reqId` acks, the 09.1 message and the FE error handling, using the Phase 2.1 catalog; port 8088 and the user's nginx are not touched; no token in a URL (confirm travels in the JSON body, never in the path or query).

Design decisions made here:
- The policy stage runs first in `AgentApi.execute` (after the operation is resolved, before the idempotency cache, before any lookup), so a refused request is never cached, never consults the registry and never starts a process. Refusal is `USAGE` with the existing message form (for agent.kill: `killSession requires confirm: true`, built from the catalog's `ws.when.field` and `confirmParam`, which keeps the 09.1 message byte-identical) and one `console.warn` line with the operation, the surface-neutral code and the agent id truncated to 64 characters.
- `confirm` means "exactly the boolean true". Package validators already reject non-booleans on the wire (USAGE from validation), and the policy rejects absent and false; the service keeps its own identical gate so direct callers cannot skip it.
- The HTTP form is `POST /api/agents/:id/kill` with `{ "confirm": true }`: a distinct route from `DELETE /api/agents/:id` (which is `agent.close`) because each HTTP route belongs to exactly one operation (spec 4.3 rule). A body `killSession` is ignored (the route implies it). Adding an HTTP binding to the catalog is additive (`contract:check` reports "binding added"); the recorded intent in the catalog ("Phase 6 adds one additively") is fulfilled.
- Fail closed: building the rules from a catalog in which a destructive operation lacks a `confirmParam` throws at startup.

Reversibility: `costly` for the catalog binding and route (a new public route in the contract and the surface snapshot; undoing it is a catalog edit, a snapshot regeneration and a router edit, and clients that adopted it would break). The policy stage itself is `reversible`.

Coverage (source audit): GOAL and success criterion 7 (destructive operations enforced at the gateway from the catalog's destructive flag, typed agent:error without a valid confirm token, FE modal UX only, adoption of the 09.1 message) and criterion 1/6 consistency (HTTP wrapper stays thin) are covered here; REQ GW-05. Phase 21's criterion 4 (the walk covers every surface, MCP included) is extended later by 21.1; this plan leaves the explicit exemption marker. Not planned: authentication (Phase 8), an MCP handler (Phase 21.1), changing the 09.1 FE flow (no FE change: the modal already sets confirm).
</objective>
