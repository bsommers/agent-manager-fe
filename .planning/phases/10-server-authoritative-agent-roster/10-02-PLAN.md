<objective>
Pin the gateway behavior that plan 10-01's roster slice relies on, and document the slice (UX-02 evidence and documentation for the pulled-forward Phase 10).

Purpose: 10-01 treats `agent:init_list` as the full snapshot the gateway sends after every create, kill and new connection, matches a pending create to the new agent by name, mode and targetHost, and treats `agent:update` as unsupported. Existing server tests only check that a create is followed by a non-empty list. This plan makes those facts executable (characterization tests, no server source change) so that Phase 6, which replaces the snapshots with `agent:added/removed/updated` and `reqId` acks, changes them deliberately, and brings the docs and the manual QA plan in line with the new live-mode behavior.

Output: `server/__tests__/rosterContract.test.ts` and edits to four docs. It touches nothing under `server/src`, `src/`, `packages/protocol/**`, root `package.json`, lockfiles, `vite.config.ts` or `.github/**`, so it runs in parallel with plan 10-01 and with 02-03.

If a characterization test fails against the unmodified gateway, the FE plan's assumption is wrong: do not edit `server/src`; correct the test only if it misread the code, otherwise record the divergence under Deviations in the SUMMARY so the 10-01 reconcile rule is revisited before merge.

Deferred (not here): `agent:update` support and tests of added/removed/updated messages (Phase 6), auth (Phase 8), hello handshake tests (Phase 8), any gateway fix for the ghost agent registered before a failed driver spawn (Phase 6, typed create errors).

Coverage (source audit): GOAL covered together with 10-01; REQ UX-02 documentation and gateway-contract evidence covered here; no RESEARCH.md or CONTEXT.md exists for this phase; Level 0 discovery, no registry package.

    - snapshot on connect: after two agents were registered through the SessionManager that bootstrap returns (createAgent called directly), a new client's first frame is an agent:init_list listing exactly those two agents with their name, mode, targetHost and status running, and distinct non-empty string ids
    - create is announced to everyone: client A sends { type: 'agent:create', name, mode: 'tmux', targetHost, initialCmd }; both A and a second connected client B receive an agent:init_list that contains an agent with exactly that name, mode and targetHost and a server-assigned id (a non-empty string); the roster in the snapshot is the whole roster, not a delta
    - initialCmd reaches the session: shortly after that create the captured driver's write mock was called with the command followed by a newline (wait with a bounded poll, the gateway delays it by 500 ms)
    - identical creates make two agents: two creates with the same name, mode and targetHost yield two entries with different ids in the next snapshot
    - kill: A sends { type: 'agent:kill', agentId } and both clients receive an agent:init_list without that id while other agents remain; the driver close mock was called; killing an id the gateway does not know still answers every client with an agent:init_list whose agent ids are unchanged
    - resync after reconnect: client A creates an agent and disconnects; a fresh client C connecting afterwards receives, as its first frame, an agent:init_list containing that agent exactly once with all ids unique
    - driver exit: invoking the captured onExit callback of the agent's driver makes every client receive { type: 'agent:status_change', agentId, status: 'disconnected' }, and a client that connects afterwards sees that agent with status disconnected in its first snapshot
    - agent:update is unsupported today: after a valid { type: 'agent:update', agentId, name: 'Renamed' }, no frame arrives within 200 ms and a client that connects afterwards sees the original name (the test name states that this pins the Phase 6 deferral)
  </behavior>
